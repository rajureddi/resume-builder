P1 means address before relying on the generated resume or stored data. P2 means address in the next product/reliability pass. References use repository-relative paths and one-based line numbers.

| P1 | **Summary trimming corrupts technology names and removes useful content.** `lib/tailor.ts:191` treats every dot as sentence punctuation. Reproduction: `Node.js and Next.js` becomes `Node. js and Next. js` after the four-sentence cap. The generated Frontend summary visibly contains `Next. js`. | Use sentence segmentation that preserves abbreviations, decimals, URLs, and technology names. Enforce a word budget as well as a sentence budget, without cutting phrases mid-sentence. |
| P1 | **The AI rewrite receives unsupported skills as ordinary JD keywords.** `app/api/tailor-resume/route.ts:54` sends `tailored.gaps.concat(tailored.skills.slice(0, 10))`. Accepted summaries/bullets are checked mainly for string length, not factual claims. | Send job requirements separately from verified candidate evidence and unsupported requirements. ## Proposed resume and summary improvements

Start with three professional, ATS-friendly layouts using the same content and export contract:

1. **Classic ATS:** compact single column, standard headings, restrained rules, readable 10.5–11 pt body text.
2. **Modern Professional:** polished header, grouped skills, optional restrained accent, clear spacing and section hierarchy.
3. **Technical Developer:** prominent relevant projects and experience, concise stacks, usable GitHub/portfolio links, evidence-focused bullets.

Store template, A4/Letter page size, section order/visibility, font, margins, and spacing per resume. Show the actual page count and warn about overflow. Do not shrink text until it becomes unreadable or remove content silently.

For summaries, aim for 2–3 sentences around 45–65 words, adjusted to the candidate and available evidence. Include role-relevant capabilities and at most one concrete accomplishment; omit missing skills, invented metrics, generic praise, and application language. Let the user edit or regenerate the summary independently before saving.

Example direction based on the seeded Frontend project facts, subject to the owner's verification:

> Software engineer with project experience building React interfaces and full-stack applications using TypeScript and FastAPI. Developed a stock-analysis platform and a real-time traffic-monitoring dashboard, with additional experience designing entity-filtering and batch-processing interfaces. Focused on practical user workflows and connecting frontend features to backend services.

## Recommended implementation sequence

1. Fix sentence/keyword matching and the summary evidence contract; add focused regressions for JavaScript/Java, Next.js/Node.js, supported vs missing skills, and word limits.
2. Add complete saved-resume snapshots and editable drafts; preserve uploaded content in Auto-Fix.
3. Implement the three layouts with consistent preview/print/PDF/DOCX rendering and page-count checks.
4. Repair persistence, API validation, and failure handling; add transactional storage verification and update vulnerable dependencies.
5. Add a working lint command and a small regression suite covering summary quality, snapshot consistency, content preservation, and export pagination. Split the 2,000-line `components/App.tsx` along actual screens/editor/export responsibilities while doing this work.

The existing Next.js app, editable project library, deterministic keyword scorer, and working file exporters are a useful foundation. A full rewrite is not necessary to begin these fixes.
